## 3. 追加DBテーブル

**savings** は本人の積立、**expenses** は本人の支出です。別テーブルにすることで、お金を入れた記録と使った記録が混ざらず、それぞれ合計・編集できます。

savingsの `oshi_id=NULL` は全推し共通の積立です。特定の推しIDがあれば、その推し用の積立になります。積立モードを選ぶ設定はなく、1件ずつ対象を選びます。

expensesも共通・未指定をNULLで保持できます。関連イベントと遠征は任意。`room_expense_id` は将来用のNULL列で、Phase 6のAPIは部屋の支出を受け付けません。

## 4. migrationと金額型

`007_money_management.sql` を **oshilife_v2** に適用済みです。既存DBのDROP、既存行の削除、既存の予約金額型の変更は行っていません。この環境で再実行する必要はありません。

金額型は既存の交通・宿泊に合わせた **DECIMAL(12,2)**。1件の上限は9,999,999,999.99円、0円も登録可能です。画面は整数円なら小数を出さず、端数がある場合だけ小数2桁まで表示します。予約に24000.50円が入っていても、反映時に切り捨てません。

API入力は整数または小数2桁までの文字列。フォームからは常に文字列で送ります。金額のAPI出力も小数2桁の文字列です。残高は100分の1円単位の整数で加減算し、浮動小数の誤差を避けます。特効の発数だけは比率として小数で計算します。

新規構築にはschema.sql、既存Phase 5環境には007を1回使用します。遠征画面にもexpenses参照を追加したため、コードを使う前にmigrationを適用してください。

## 5. INDEX / UNIQUE

INDEXは検索条件に合う行を探すための目印、UNIQUEは重複を拒否するDBの制約です。

| テーブル | 制約・目印 |
| --- | --- |
| savings | 本人＋日付、本人＋推し＋日付、推しのINDEX |
| expenses | 本人＋日付、本人＋推し＋日付、本人＋カテゴリ＋日付、本人＋特効対象＋日付のINDEX |
| expenses | 推し・イベント・遠征のINDEXと外部キー |
| expenses | **user_id＋source_type＋source_idのUNIQUE** |

手入力のsource_idはNULLなので、手入力支出は何件でも登録できます。反映元のsource_idは、交通・宿泊の物理削除後も会計記録を維持するため、予約テーブルへの外部キーにはしていません。反映するときにPHPで元予約→遠征→本人を確認します。イベント・遠征への関連は外部キーで保持します。

## 7. 積立の仕組み

```text
ユーザー → saving_form.phpで金額・積立日・対象を入力
  → money.js → savings/create.php
  → セッション本人確認・CSRF → 入力検証
  → savingsに保存 → JSON応答 → 年間画面を再取得
```

共通と推し別を同時に持てます。登録解除した推しの過去記録も全推しの集計に残り、その記録の編集画面から修正できます。新しく対象を変える場合は本人の登録済み推しから選びます。

## 8. 支出の仕組み

```text
ユーザー → expense_form.phpで支出を入力
  → カテゴリで特効対象の初期値を表示
  → expenses/create.php → 入力・本人・関連先の確認
  → expensesへ保存 → 年間集計を更新
```

カテゴリはconfig/money.phpで管理します。直接の推し活7カテゴリは特効対象の初期値がtrueで、利用者が外すこともできます。手数料・交通・宿泊・食事・観光・その他遠征はfalse固定で、改ざんしたtrueもPHP側で拒否します。

関連イベントを選ぶ場合は同じ推しを、遠征を選ぶ場合はその遠征に対応するイベントを選んでください。他人の遠征を指定することはできません。イベントの共有内容が後から変わっても、既存支出の対象を勝手に付け替えません。

## 9. 前年繰越

選択年の1月1日より前の積立合計から、同じ期間の支出合計を引きます。

```text
前年繰越 = 選択年より前の積立累計 − 選択年より前の支出累計
```

年度締めテーブルや繰越のコピー行は作りません。過去の記録を修正すると、翌年以降の繰越も再計算されます。残高がマイナスならそのまま負の金額として扱います。

## 10. 現在残高

```text
前年繰越 ＋ 選択年の積立 − 選択年の支出 → 現在残高
20,000円 ＋ 100,000円 − 58,000円 → 62,000円
```

画面の「今年」は選択年を指します。登録した日付で年全体を集計するため、選択年内の将来日付の記録も含みます。ホームは現在年を使います。通貨表示は `¥62,000`、負なら `¥-25,000` のように表示します。

## 11. 全推し / 推し別集計

全推しでは共通分を含む本人の全積立・全支出。特定推しではそのoshi_idの積立・支出だけを繰越から一貫して集計します。

共通積立を人数で割ったり、各推しへ重複加算したりしません。推し別画面には「今年の共通積立」「前年までの共通積立累計」を参考表示します。これらは積立そのものの額で、共通支出を差し引いた残高ではありません。ホームでも「共通積立は含みません」と表示します。

## 12. 月別 / カテゴリ別 / 推し別集計

**SUM** は指定した列の合計、**GROUP BY** は同じ月・カテゴリ・推しの行をグループに分けるSQLです。

```text
本人の対象年のexpenses
  ├─ 全件SUM → 年間支出
  ├─ 月ごとGROUP BY＋SUM → 1〜12月の支出
  ├─ categoryごとGROUP BY＋SUM → カテゴリ内訳
  └─ oshi_idごとGROUP BY＋SUM → 推し別内訳
```

月別は0円の月も12ヶ月すべて表示。カテゴリは0円をグラフから省きます。推し別は全推し表示時にだけ表示し、名前順の内訳で金額順位にはしません。CSSの棒と金額ラベルを使い、新しい外部グラフイベントラリは追加していません。

## 13. 遠征費からexpensesへの反映

追記：反映条件は[支払い連携ガイド](PAYMENT_IMPORT.md)のとおり、予約済み・支払い済み・金額>0に限定しました。チケットも入金TODOから反映できます。

```text
本人のtransportation / accommodation
  → 遠征まとめの「お金管理に反映」
  → expense_form.phpで名前・日付・金額・推し・イベントを確認
  → 利用者が保存を押す
  → 元予約の所有者を再確認 → expensesへ登録
```

確認画面を開いただけでは支出は作られません。金額未設定や予約キャンセル中のものには反映ボタンを出しません。キャンセル料などは必要に応じて手入力の支出として記録できます。

反映した支出は**確認時の内容を保存した記録**です。元予約の金額変更・予約削除・キャンセルで支出を自動更新しません。反映後の金額修正・削除は支出側で行います。二重に課金されたような集計や、記録の予期しない消失を防ぐためです。

反映元由来の推し・イベント・遠征・カテゴリは固定し、支出名・金額・日付・メモは編集できます。交通・ホテルは特効対象外です。

## 14. 二重登録防止

source_typeにmanual／live_ticket／transportation／accommodation、source_idに元の個人管理・予約IDを保存します。本人＋種類＋元IDのUNIQUEにより、同時に2タブから保存しても1件しか作れません。2回目の保存は409で案内し、遠征画面のリンクは「登録済みの支出を編集」へ変わります。

支出を削除した場合はその反映記録もなくなり、元予約が残っていれば再確認して再登録できます。有効な支出が同じ予約から二重になることはありません。手入力支出と元予約の同一性までは自動推測しないため、すでに手入力した費用を重ねて反映しないよう内容を確認してください。

## 15. 特効換算

`special_effect_eligible` は登録時の判定を保持する列です。現在のカテゴリ設定だけで毎回再判定すると、将来ルールを変えたときに昔の換算額まで変わるため、支出と一緒に保存します。

```text
expenses → 本人・選択年・推しで絞る
  → special_effect_eligible=true の金額をSUM
  → 対象額 ÷ config/money.phpの基準額
  → 炎 / CO₂ / 銀テのタブで表示
```

| 特効 | 基準 | 対象45,000円の例 |
| --- | --- | --- |
| 炎 | 100円。1台・1発の燃料相当 | 約450発 |
| CO₂ | 300円。1台・約1秒噴射 | 約150発 |
| 銀テ | 4,000円。キャノン1台・1回、約20〜25本 | 11.25発 → 表示は約11.3発 |

基準はユーザー指定の遊び用目安であり、実際の演出価格を取得・見積もる機能ではありません。対象額・1発の基準・定義を表示し、「換算について」を開くと指定の注意書きを全文確認できます。

> ※特効換算は、炎の燃料・CO₂ガス・銀テープなどの消耗品価格を参考にしたOshilife独自の目安です。実際のライブ演出では、使用する機材や演出内容によって消耗量が異なるほか、人件費・機材費・運搬費・設営費等が別途必要となるため、実際のライブ演出費とは異なります。

## 16. セキュリティとコードの読み方

- **セッション**はサーバーがログイン済みの本人を覚える仕組みです。既存の認証middleware（ページやAPIの前で行う共通チェック）が本人を確認し、user_idを渡します。URLのuser_idは使いません。
- 閲覧・編集・削除は記録IDと本人IDの両方をSQL条件にします。他人のIDは404で拒否。交通・ホテルも必ず遠征のuser_idまで辿ります。
- **CSRFトークン**は画面に渡した確認用文字列です。Cookieだけを利用する第三者サイトからの勝手な保存を防ぐため、POSTで照合します。
- **PDOプリペアドステートメント**はSQL命令と入力値を分ける仕組みです。値をSQL文字列へ直接埋め込まず、SQLインジェクションを防ぎます。
- **トランザクション**は一組の処理を全部成功か全部取り消しかにする仕組みです。保存・削除と、複数の年間集計を一貫した状態で扱います。
- PHPの `e()` は **htmlspecialchars** でタグを文字へ変換し、JavaScriptはtextContentを使用。支出名・メモにタグが入っても実行しません。
- `.env` はDB接続・APP_URLなど環境別の設定です。公開・Git保存はしません。リンクとAPIパスは既存のappUrl、CSS/JSはassetUrlを使い、localhost配下で整合させています。
- ログインは既存のpassword_hash（原文を保存しないためのパスワード要約）、password_verify（入力との照合）、session_regenerate_id（ログイン時の識別子更新）を引き続き利用しています。

今回の**API**はJavaScriptから呼び出してJSONを返すPHPの入口です。画面と保存処理を分けることで、ホームとお金画面で同じ計算を共用できます。

```text
money.php → middlewareで本人確認 → HTML表示
  → money.js → public/api/money/dashboard.php
  → api/money/dashboard.php → money_api.php
  → money_service.phpのフィルタ検証
  → money_repository.php → PDO → MySQL
  → JSON → 数字・棒・特効を表示
```

今後カテゴリや換算値を増やすならconfig、入力ルールはvalidator、保存手順はservice、検索・集計はrepository、見た目と操作はmoney.php・money.js・money.cssへ追加します。適用済みmigrationの改変ではなく、新しいmigrationでDBを拡張します。

## 19. ブラウザで確認する手順

1. Apache・MySQLを起動し、localhostにログイン。マイページ→お金管理を開きます。下部ナビは5項目のままです。
2. 共通積立、推しA用積立、推しB用積立を作ります。編集・削除ができることを確認します。
3. 前年の積立30,000円と支出10,000円、対象年の積立100,000円と支出58,000円を登録すると、繰越20,000円・残高62,000円になります。実データに混ぜたくない場合は検証用アカウントで試してください。
4. 年と推しを切り替えます。推し別残高に共通積立が入らず、参考表示されることを確認します。月別12ヶ月・カテゴリ内訳・全推し時の推し内訳も確認します。
5. 支出をグッズにすると特効対象がオン、交通・宿泊にするとオフになることを確認。対象45,000円なら炎450発、CO₂150発、銀テ約11.3発です。「換算について」の注意書きも開きます。
6. 遠征まとめで交通・ホテルの「お金管理に反映」を開きます。名前・日付・金額・関連先を確認して保存。同じ予約のリンクが「登録済みの支出を編集」へ変わることを確認します。
7. 元の予約金額を変更しても支出が勝手に変わらないこと、支出側で修正できることを確認。反映済み支出を削除すれば、残っている元予約から再確認・登録できます。
8. ホームの推し活資金に実際の金額が出て、推し切替と連動することを確認します。新着の公開予定／イベント情報や、落選を除いた次のイベントも確認します。
9. 別ブラウザ／プロファイルでBさんをログインし、Aさんのsaving_form・expense_form・sourceのURLを開いても取得できないことを確認します。
10. PCとスマホ相当の幅390px・320pxで、負の残高・長い支出名・入力・特効タブ・グラフ・ナビの表示を確認してください。
